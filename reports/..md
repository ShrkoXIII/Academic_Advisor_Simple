## A. Executive Summary

1. **العقد المطلوب ليس إرسال 47 Feature.** العدد الحقيقي 42 Numeric + 5 Categorical = 47. PHP يملك الحقائق الجامعية الحية والأهلية والسياسات، و Python يملك الـ Feature semantics، الحالة المسبقة، حساب سياق الخطط، المودلات والترتيب.
2. **المسار الحالي يتطلب توليد الخطط قبل توقع درجاتها.** هناك 14 Feature تعتمد على الخطة والمواد الأخرى فيها؛ لا يصح توقع المادة مرة واحدة ثم استخدام التوقع في جميع الخطط بالمودل الحالي.
3. **الوقت لا يُحل بتقليل Queries وحده.** تحميل المودلات والداتا لكل طلب، إعادة تاريخ الطالب، وعدد Course-in-plan rows أهم مصادر كلفة محتملة. `top_n=3` لا يقلّل عدد الخطط التي تُقيّم.
4. **Frozen History الحالي إحصاءات مقررات مجمّعة فقط.** ينتج 7 Features؛ لا يحتوي State شخصيًا للطالب أو المحاولات أو GPA أو موازنة متطلبات التخرج. نحتاج States منفصلة.
5. **إضافة عمود إلى View مناسبة عندما توفر حقيقة موجودة أو Lookup بسيطًا موثوقًا.** نقل تجميع تاريخ كامل إلى View عادي قد ينقل الكلفة إلى DB دون تقليلها. الحسابات البسيطة مثل Ratio و Trend و Semester تُشتق محليًا؛ التجميعات المتكررة تُحسب مسبقًا.
6. **الداتا ليست جاهزة لاعتبار `20261` فصلًا مكتملًا.** Raw status فيه صفّان لـ 20261؛ Clean status فيه صف واحد؛ لا يوجد Target status لـ 20262. Raw course فيه 20253 لكن Features تستبعده باعتباره غير مكتمل. أحدث History bundles موجودة: 20243 و 20251 فقط.
7. **الـ History validator الحالي لا يدعم تلقائيًا Latest finalized semester.** Target 20262 يطلب History 20261 افتراضيًا حتى لو لم يُقفل. يلزم لاحقًا سياسة تفرّق بين آخر فصل تقويمي وآخر فصل مكتمل؛ لا تُرفع Incomplete outcomes للتحايل على الفحص.
8. **هناك TRAIN/SERVE SKEW فعلي في المحاولات.** التنظيف يعدّ تسجيلات قبل استبعاد بعض نتائجها؛ التوصية تعتمد Max من التاريخ المنظّف المتبقي. إعادة منطق Serving على 456,595 صفًا منظفًا خالفت Attempt المحفوظ في 17,938 صفًا. هذا تشخيص للبيانات، لا نسبة فشل توصيات.
9. **معلومات المتطلبات موجودة جزئيًا:** `credits_count` في الكتالوج لكل Requirement و`requirement_passed_credits` في Request. لا يجوز استنتاج أن Required credits هي Hard maximum، أو أن Candidate procedure تفحص مجموع الخطة أو الاستثناءات؛ تعريف ذلك يحتاج الجامعة.
10. **نعم، يمكن إعطاء الأدمن زر تحديث State/History وزر إعادة تدريب.** ينفّذ كل منهما Job منفصلًا خارج طلب التوصية، يبني إصدارًا جديدًا ويفحصه قبل النشر. تحديث History لا يعني Retraining. التدريب الحالي يكتب إلى Paths فعالة ويستخدم فصولًا ثابتة؛ لا يصلح تغليفه مباشرة بزر Production.

### الوقت وتقليل Queries: القرار المقترح

المسار الافتراضي: **PHP يجمع Context من النظام الجامعي ويرسله مرة واحدة إلى Python**، لأن PHP يملك اتصال الجامعة وهوية الطالب ويستدعي مصدر المرشحين. يمكن لاحقًا استخدام Context reference إذا جرى تخزين Snapshot آمنًا ومؤرشفًا؛ Reference صغير لا يلغي كلفة إنشائه.

| خطوة | مسار الطلب المقترح | ما يُمنع تكراره |
|---|---|---|
| Models / Categories / GradeScale | تحميل وفحص مرة لكل Worker عند Startup أو تغيير إصدار | قراءة الملفات والـ Hashes مع كل طلب |
| Course History | إصدار Immutable محمّل، Apply على المرشحين مرة | إعادة تجميع كل Outcomes |
| Catalog | Map أو Table محمّل بمفتاح Version + Degree + Course | إرسال صف الكتالوج لكل مادة، Query لكل Candidate |
| Student / Student-course state | Lookup واحد للطالب + Batch lookup لكل Candidate IDs | التاريخ الكامل و Sort/Groupby/Shift لكل طلب |
| Candidate source | Capture واحد مع Identity/Target/Revision | Procedure لكل خطة أو كل مادة، ثم Python يعيد طلب المصدر نفسه |
| Policies / Requirement balances / GPA | Bundle واحد أو Revisions مؤرشفة | تكرار حقول الطالب والسياسة عبر صفوف المواد |
| Models | Predict Grade و Fail على Batch من Course-in-plan rows | HTTP أو Predict منفصل لكل صف |
| Response | Top plans وتفاصيلها و Provenance | إرجاع كل Rows/Plans إلى PHP افتراضيًا |

هدف النقل هو **استدعاء PHP→Python واحد** للتوصية، و**Capture منطقي واحد** للمرشحين. هذا لا يعني SQL Query واحدًا: Procedure و Views قد تنفذ Queries داخلية عديدة. اختاروا الاستعلامات وفق Execution plans، حجم Rows، Rows examined، DB CPU، Locks و p50/p95/p99؛ لا تعيدوا Join ضخمًا يكرر Student snapshot 100 مرة فقط لتقليل عدّاد Queries.

زمن الطلب يُقاس كمراحل: `context_capture + state_lookup + candidate_enrichment + enumeration + feature_context + two_model_predictions + ranking + serialization`. لا يوجد SLA مثبت حاليًا. نتيجة محفوظة سابقة لـ 15 Candidate تضمنت 2,503 خطة و`elapsed_seconds≈0.460` داخل Engine؛ لم أشغّلها الآن، ولا تشمل هذا الرقم DB/network/load/ضغط المستخدمين، فلا يصلح وعدًا بزمن Production.

عدد الخطط Exhaustive وقابل للنمو الأُسّي حتى مع Credit pruning؛ الحدود والصفر Credit courses تزيد حالات معينة. الـ Batch الافتراضي 2,000 **خطة**، وليس 2,000 صف؛ عدد Rows يساوي مجموع مواد هذه الخطط. `top_n` يحدّ الإرجاع فقط. أولوية تحسين لاحقًا: Filtering لسياسات مؤكدة قبل Scoring، ثم Context vectorization وتجنّب نسخ Frames، ثم التعامل مع الازدحام و Timeout واضح. لا تقليص مرشحين أو خطط أو تغيير مودل لضمان زمن صغير دون قرار منتج و Validation؛ إذا توقف الحساب فلا تسمِّ Partial top plans نتيجة Exhaustive مكتملة.

### متى نضيف Column إلى View؟

| حالة | القرار | السبب |
|---|---|---|
| `grade_version_id` و Start totals موجودة في STATUS | إعادة استخدام المصدر، أو تضمينها في Snapshot view | لا حاجة لحسابها من Transcript داخل ML |
| `faculty_id` للدرجة الحالية | Lookup جامعي/Join موثوق في Snapshot | المصدر المحلي الحالي COURSE؛ استنتاجه من تاريخ الطالب يفشل للطالب الجديد |
| آخر GPA مسجَّل وما قبله | DB State أو ML State متكافئ، أيهما أرخص تشغيليًا | يجب تجاوز فصول غير المسجَّل؛ Raw `prev_gpa_points` ليس بديلًا مضمونًا |
| Attempt counter | Counter/State محدث بالتسجيلات أو Materialized result | `ROW_NUMBER/COUNT` على تاريخ كامل في View عادي قد يعيد الكلفة لكل طلب |
| Ratio/Trend/Target semester | Python من قيم موجودة | حساب O(1)، منع تكرار Fields وتباين التعريف |
| Requirement completed balance / GPA denominator / Exceptions | المصدر الجامعي الرسمي | قواعد احتساب الإعادات والتحويلات ليست معرفة داخل ML |
| Course statistics / 14 plan-peer features | Python | إحصاءات Versioned مطابقة للتدريب، وسياق الخطة غير موجود قبل توليدها |

الاختيار ليس «DB دائمًا أسرع» أو «Python دائمًا أسرع». إذا كان الـ Backend يملك Summary رسميًا مضبوطًا فلا نبني Summary منافسًا. وإذا كان Column جديدًا ينفّذ History scan في كل SELECT فالحل State/جدول Summary/Materialized view وتحديثه، وفق قاعدة البيانات الفعلية التي لم يثبت نوعها من المشروع.

للخدمة المستمرة، تحميل ML resources عند `lifespan` تدعمه [وثائق FastAPI الرسمية](https://fastapi.tiangolo.com/advanced/events/). كل Process قد يملك نسخة خاصة؛ زيادة Workers تتطلب ميزانية RAM و CPU و LightGBM threads. `async` وحدها لا تخفض كلفة الحساب الأُسّي.

### ما أثبتته القيم الفعلية

- Clean V2: Status107,939؛ Course456,595؛ Diploma32,524؛ Catalog4,006؛ Roster474,165. Features train356,816×95 و test67,536×95. الـ 95 ليست Features المودل؛ مدخلاته 47 فقط.
- Raw status20251=8,123؛20252=7,573؛20253=4,664؛20261=2. Raw course20253=12,768. وجود Rows لا يثبت اكتمال Results.
- Catalog لديه 295 مجموعة `(degree,requirement)`، `credits_count` ثابت داخلها جميعًا. في 139 مجموعة مجموع ساعات كل المواد أكبر من Quota. مثال Degree42.111/Requirement2:13 مادة، مجموع 26 ساعة، Quota4.
- مجموع Quotas الفريدة لكل Requirement طابق `degree_credits_count` في 50/50 درجة موجودة في Clean status. يجوز Precompute degree total من Catalog إذا صار هذا Invariant جزءًا من Contract؛ المسار الحالي يأخذه من Status.
- `start_total_in_credits != total_reg_credits` في 83,874 من 107,939 صف Status. لا تخلط ساعات in-credits بساعات التسجيل؛ ولا يوجد برهان أن أيهما هو GPA denominator الرسمي.

### attempt_number: القرار المدعوم بالأدلة

الدالة `clean_student_course()` في [clean_student_course.py](<D:/AI/Real projects/Academic_Advisor_Simple/src/data/clean_student_course.py:72>) تحتفظ أولًا بالصفوف ذات `register_status ∈ {R,E}` و`part_id > 20193`، وتتحقق من المفاتيح. ثم ترتب ترتيبًا ثابتًا حسب **`student_id, course_id, part_id`** وتحسب `cumcount() + 1` داخل كل Student + Course، عبر الدرجات. لا يدخل `student_course_id` في هذا الترتيب. **بعد حساب العداد** تستبعد الصفوف ذات Finish status خارج P/F/FE/FA، والصفوف التي تحتوي N في أعلام In-GPA أو In-AGPA أو In-Credits. لذلك قد يعكس `attempt_number` محاولة سابقة لم يعد صفها موجودًا في المخرجات المنظفة.

أما Serving في [inputs.py](<D:/AI/Real projects/Academic_Advisor_Simple/src/recommendation/inputs.py:113>) فيقرأ `max(attempt_number)` من Clean rows التي تحقق `part_id < target_part`، ثم يضيف 1. مثال فعلي: الطالب `10003.111` والمادة `678.111` لديهما تسجيل R بنتيجة Z في 20222 و 20223، ثم تسجيل R بنتيجة P في 20231. العداد في Cleaner يساوي 3، لكن حساب Serving عند 20231 يعطي 1 لأن صفَّي Z غير موجودين في Clean history.

عند إعادة تطبيق حساب Serving على كل صف محفوظ، اختلفت النتيجة عن العداد الموجود في **17,938 من 456,595 صفًا**، تغطي **17,518 مفتاح Student + Course**. وعند Cutoff هدفه 20262، اختلف عداد Raw R/E بعد 20193 عن أقصى عداد محفوظ في Clean history على **33,727 من 441,549 مفتاحًا**؛ منها **28,191 مفتاحًا** لا تحتوي إلا على محاولات مستبعدة من Clean history. هذه المفاتيح ليست كلها Candidates، ولذلك لا تمثل هذه الأعداد معدل خطأ في التوصيات.

**الاقتراح للإنتاج:** حفظ State مسبق لعداد الطالب والمادة مع تعريف صريح للعداد ونطاق Coverage، وتحديثه عند تغيّر التسجيل. يُجرى Batch lookup للمواد المرشحة عند الطلب. إذا كان Backend يملك عدادًا موثقًا بالتعريف نفسه، يمكنه توفيره في Student-course summary بدل حفظه في ML State؛ المصادر الخام المحلية لا تثبت وجود مثل هذا الحقل. لا نحتاج إرسال Transcript كامل مع كل طلب.

يوجد خياران مختلفان يجب إظهارهما بوضوح. حفظ `last_retained_attempt` يحافظ على سلوك Serving الحالي. أما حفظ عداد جميع تسجيلات R/E ضمن حدود التدريب فيحافظ على Training count، ويغيّر Serving في الحالات الموثقة أعلاه. إصلاح هذا الاختلاف يحتاج لاحقًا تغييرًا صريحًا وفحص Regression؛ لا يصح اعتبار الخيارين متكافئين. كذلك فإن احتساب كل المحاولات قبل 2020 أو احتساب مرات النجاح فقط يغيّر Training semantics الحالية.

### observed_gap_semesters

[academic_calendar.py](<D:/AI/Real projects/Academic_Advisor_Simple/src/data/academic_calendar.py:19>) يعد الفصول العادية 1 و 2 الواقعة **بين آخر فصل مسجل مشاهد والفصل الحالي، دون احتساب الطرفين**. الفصل الصيفي 3 غير المسجل لا يزيد Gap؛ أما الصيفي المسجل فيحدّث آخر Enrolled part. وإذا كان صف STATUS الحالي لفصل عادي غير مسجل، يضيف Cleaner مقدار 1. وعند غياب تسجيل سابق مشاهد تبقى القيمة Unknown.

المدخلات الدنيا هي `last_observed_enrolled_part` من State، و`target_part`، وسياق تسجيل فصل الهدف. لا نحسب Gap بعدّ صفوف STATUS المفقودة أو بطرح أرقام الفصول مباشرة. مثال الكود الحالي: الانتقال من آخر تسجيل في 20221 إلى 20232 يعطي **Gap = 2** بسبب الفصلين العاديين 20222 و 20231.

عند التوصية لفصل مستقبلي قبل التسجيل، يلزم تحديد ما إذا كان الهدف سيُمثَّل كفصل ينوي الطالب التسجيل فيه أم كصف STATUS غير مسجل. هذا الاختيار قد يغيّر Gap بمقدار 1، ولا يمكن استنتاجه تلقائيًا من الفصل الحالي.

## G. Runtime Features

وقت طلب التوصية فقط: توحيد IDs، التحقق من Context versions، حساب `part_semester` و Ratio/Trend/Missing flags، و Attempt lookup+1، ثم Catalog join و History apply مرة للمرشحين. بعد توليد الخطط تُحسب 14 Plan/Peer features **لكل خطة**، ثم Grade/Fail predictions، و GradeScale conversion، و Plan GPA/Projection/expected failed credits، والترتيب.

لا حاجة إلى Backend queries بعد توليد الخطط، أو Query داخل `score_rows()` أو داخل حلقة المواد. لا تُحدَّث State من Predictions. يمكن تخزين Course history lookup و Catalog enrichment مؤقتًا بحسب Full context revision؛ أما Plan prediction فلا يصح تخزينه بمفتاح Student+Course فقط.

Cache مقترح:

- Artifacts: Release/hash؛ Catalog: Version+Degree؛ Student: Revision؛ SC: Revision+Course IDs؛ History: Release/cutoff.
- Candidate: Student+Degree+Target+procedure revision+Snapshot revision+policy/exception versions. يُلغى عند تغيير التسجيل أو نتائج المتطلبات السابقة أو الكتالوج أو الاستثناء. TTL وحده لا يثبت الأهلية.
- Final recommendation: Full context hash + requested credits mode + official model/category/GradeScale/history/catalog/engine/policy versions + top_n. تغيّر أي Dependency يعيد الحساب؛ Cache hit لا يبرر استخدام State مختلفة بصمت.
- يمكن لاحقًا إزالة تكرار 47-feature vectors المتطابقة تمامًا داخل Batch وإعادة توزيع predictions إذا ثبتت Prediction parity. هذا تحسين غير منفذ، ولا يعني توقعًا واحدًا لكل Course.

### المدخلات والمجاميع المخزنة

يحتاج البناء إلى تسعة أعمدة فقط، كما يحدد [HISTORY_SOURCE_COLUMNS](<D:/AI/Real projects/Academic_Advisor_Simple/src/features/frozen_history.py:28>):

```text
student_course_id, part_id, degree_id, course_id, faculty_id,
plan_requirement_type_id, course_credits, attempt_number, final_mark
```

يخزن خمس جداول تجميع، بالإضافة إلى مجاميع عامة:

| مستوى fallback | مفتاح التجميع |
|---|---|
| 1 | `degree_id + course_id` |
| 2 | `course_id` |
| 3 | `degree_id + plan_requirement_type_id + rounded(course_credits)` |
| 4 | `faculty_id + plan_requirement_type_id + rounded(course_credits)` |
| 5 | `plan_requirement_type_id + rounded(course_credits)` |
| 6 | المجاميع العامة Global، عند غياب المفاتيح الخمسة |

التقريب هنا هو `pandas.round()` المستخدم حاليًا، وتتحول القيم المفقودة داخل المفاتيح إلى `__MISSING__`. تغيير طريقة التقريب أو تركيب المفاتيح يغيّر semantics التاريخ؛ المصدر هو [build_history_keys](<D:/AI/Real projects/Academic_Advisor_Simple/src/features/temporal_features.py:64>).

لكل مفتاح وللمستوى العام، تُخزن ستة مجاميع:

```text
effective_support = Σ weight
raw_count         = Σ 1
mark_sum          = Σ (final_mark × weight)
fail_sum          = Σ ((final_mark < 50) × weight)
attempt_sum       = Σ (attempt_number × weight)
retake_sum        = Σ ((attempt_number > 1) × weight)
```

الوزن `0.25` للسنوات قبل `2022`، و`1` من `2022` فما بعد. **لا يوجد تناقص للوزن مع عمر الفصل أو بُعده عن target.** المتوسطات والنسب تُستخرج من المجاميع عند `apply()`؛ لا تُخزن هنا كصفوف تاريخية للطلاب. الدليل: [temporal_weight](<D:/AI/Real projects/Academic_Advisor_Simple/src/features/temporal_features.py:59>) و[CourseHistoryState.update](<D:/AI/Real projects/Academic_Advisor_Simple/src/features/temporal_features.py:115>).

### ما تنتجه apply()

تختار `apply()` أكثر مفتاح محدد موجود، ثم تحسب أربعة متوسطات أو نسب:

```text
value = (local_sum + 20 × global_mean) / (local_support + 20)
```

يستخدم كل مستوى المتوسط العام نفسه كـ prior؛ لا يوجد smoothing متسلسل عبر المستويات. عند غياب كل المفاتيح، تُستخدم المتوسطات العامة مباشرةً ويكون fallback level هو `6`. الدعم المعلن هو الدعم المحلي المختار قبل إضافة `20` إلى denominator.

`min_support = 20` يحدد إشارة missing فقط؛ انخفاض الدعم لا يُجبر الكود على الانتقال إلى مفتاح أوسع:

```text
course_history_missing = (fallback_level >= 3) OR (effective_support < 20)
```

المخرجات السبعة هي `course_history_avg_mark`، `course_history_fail_rate`، `course_history_avg_attempt`، `course_history_retake_rate`، `course_history_effective_support`، `course_history_fallback_level` و`course_history_missing`. الدليل: [CourseHistoryState.apply](<D:/AI/Real projects/Academic_Advisor_Simple/src/features/temporal_features.py:149>).

### التحقق، اكتمال المصدر والتصحيحات

يتحقق [build_frozen_history](<D:/AI/Real projects/Academic_Advisor_Simple/src/features/frozen_history.py:87>) من أن cutoff لا يتجاوز `finalized_through_part`، وأن المصدر يصل إلى cutoff نفسه، وأن `student_course_id` فريد وغير null، وأن القيم الرقمية finite، والعلامات بين `0` و`100` والمحاولة `>= 1`. يتحقق أيضًا من عقد feature version وهوية مصدر V2.

لكن **`finalized_through_part` شهادة من caller، وليست إثباتًا بأن الجامعة أغلقت الفصل أو أن التصدير كامل**. metadata و hashes تثبت هوية الملفات والمحتوى؛ لا تثبت closure أو coverage أو وصول كل العلامات والتصحيحات المتأخرة. حتى علامة صفر finite تعبر الفحص الرقمي، ولذلك يجب تأكيد أنها نتيجة نهائية وليست قيمة مؤقتة.

`CourseHistoryState.update()` يقبل فقط outcomes من فصول أحدث من cutoff المحفوظ. هو append-only؛ لا يخزن Row IDs لمنع تكرار delta، ولا يدعم تعديل أو حذف مساهمة قديمة. النتيجة المتأخرة لنفس الفصل أو لفصل أقدم تُرفض، وإعادة إدخال نتيجة تحت صف جديد قد تضاعف المجاميع.

أبسط خيار مقترح للإصدار الإنتاجي الأول هو بناء bundle جديدة من prefix معتمد عند إغلاق فصل أو تصحيح نتائج قديمة. يمكن إضافة incremental updates لاحقًا مع ingestion ledger و idempotency والتحقق من مساواتها لـ full rebuild. يمنع [save_frozen_history](<D:/AI/Real projects/Academic_Advisor_Simple/src/features/frozen_history.py:161>) استبدال مجلد قائم، ويكتب metadata أخيرًا كعلامة اكتمال. revision جديدة لنفس cutoff تحتاج namespace أو release root جديدة؛ `as_of_<part>` وحده لا يمثل عدة revisions. registry و workflow التصحيحات غير منفذين حاليًا.

### التوصية أثناء 20261 غير المكتمل

cutoff الآمن هو **آخر فصل له نتائج مكتملة ومعتمدة ومغطاة، متاحة في وقت الطلب، ويكون part الخاص به أصغر من `20262`**. إذا أُغلق `20253` وتأكدت تغطيته، يمكن أن ينتهي التاريخ عنده. إذا كان آخر المعتمد هو `20252`، يبقى cutoff عند `20252`. لا يجوز رفعه إلى `20261` اعتمادًا على كون هذا الفصل هو السابق تقويميًا.

[validate_history_selection](<D:/AI/Real projects/Academic_Advisor_Simple/src/features/frozen_history.py:43>) يطلب الفصل السابق **تقويميًا**، أي `20262 ← 20261`. منع نتائج target والفصول المستقبلية صحيح، لكن الكود يرفض `20253` أو `20252` افتراضيًا في هذا السيناريو. يوجد `allow_older_history=True` كاختيار صريح للتاريخ الأقدم، وتصفه الرسالة بأنه للـ backtesting؛ تفعيله خفيةً في Production لا يحل تحديد freshness. كما أن [Production Contract](<D:/AI/Real projects/Academic_Advisor_Simple/docs/PRODUCTION_CONTRACT.md:166>) يقول «previous finalized academic part»، وهو أوسع من التحقق التقويمي المنفذ.

المقترح لاحقًا هو calendar/availability manifest يثبت latest finalized cutoff والـ source revision وحدود staleness المقبولة. لا يُترك اختيار تاريخ اعتباطي للمستخدم العادي، ولا تُعد نتائج فصل غير مكتمل نهائية.

كذلك يشترط [engine.prepare_candidates](<D:/AI/Real projects/Academic_Advisor_Simple/src/recommendation/engine.py:63>) أن يكون `snapshot.part_id = target_part`، وأن يصف snapshot بداية الفصل الهدف. snapshot الفصل الحالي `20261` ليس تلقائيًا snapshot بداية `20262`؛ تغيير الرقم وحده يسبب **TRAIN/SERVE SKEW**. أمام المنتج خياران يحتاجان تعريفًا واضحًا:

1. توصية تعتمد بداية الفصل الهدف المؤكدة بعد تثبيت نتائج `20261`؛ وهي الأقرب إلى semantics الحالية.
2. توصية مبكرة أثناء `20261` تحمل `data_as_of` الحقيقي وتُعلن `provisional`، ثم تُحدّث بعد finalization. يلزم تعريف features لهذا الوضع والتحقق منها قبل الإتاحة؛ الكود الحالي لا ينفذها.

لا تُستبدل final marks في التاريخ بتوقعات، ولا تُحسب مواد `20261` كأن الطالب نجح فيها. إذا أثرت التسجيلات الحالية على أهلية مواد `20262`، يجب أن يوضح Backend وفريق الجامعة ما الذي تعنيه أهلية candidates في التوصية المؤقتة، وكيف يتعامل procedure معها.

### بعد إغلاق الفصل أو وصول تصحيح

التسلسل المقترح هو:

```text
Capture export + source revision + finalization/coverage evidence
→ Normalize and validate
→ Update student GPA/counters/attempts/requirement balances
→ Build a new Course History release
→ Verify cutoffs, IDs, hashes and reconciliation
→ Bind compatible versions in one Serving release
→ Activate atomically, warm load and invalidate affected caches
```

يبقى الطلب الجاري على إصداره المثبت. لا تُنشر حالة طالب حديثة مع requirement balances قديمة دون تعريف موحد لـ snapshot ومعرفة أثر الاختلاف.

عند تعديل تسجيل أثناء الفصل، تُحدث candidate state و attempt/gap state المعنية وفق تعريفها المعتمد؛ لا تدخل التسجيلات غير النهائية في مجاميع course outcomes. وعند تصحيح علامة قديمة، تُعاد dependencies المتأثرة وتُنتج revision جديدة، مع إبقاء artifact المستخدمة في backtest سابق محفوظة.

المواكبة لا تعني العمل اليدوي المستمر أو retraining عند كل طلب. تحديث snapshots والتسجيلات يتبع تغير المصدر؛ تحديث course history يتبع اعتماد النتائج؛ وتحديث catalog والسياسات يتبع تعديلهما. إذا تأخر state مؤثر، يجب إعادة التحقق منه، أو إعلان `data_as_of` بوضوح، أو رفض توصية تتطلب معلومات غير متاحة. التأخر المعروف في إحصاءات أداء المواد قد يكون مقبولًا وفق عقد serving، لكن تأخر صلاحية تسجيل أو استثناء أكاديمي يحتاج قاعدة مختلفة.

**Retraining قرار مستقل.** يمكن إطلاق candidate training دوريًا أو عند توفر نتائج جديدة كافية، أو ظهور drift وأخطاء segments أو calibration تستحق المعالجة، أو تغير عقد features. تحديث history بنفس التعريف، أو term policy، أو حقائق catalog لا يستلزم retraining بالضرورة، لكنه يحتاج فحص compatibility ومراقبة أثره. نجاح التدريب لا يعني ترقية المودل تلقائيًا.

### صلاحيات الأدمن والـ Jobs المقترحة

| إجراء مقترح | العملية | النتيجة |
|---|---|---|

يمكن لزر واحد أن يبدأ job كاملة للبناء والتحقق ثم نشر history وفق وصفة معتمدة. ويمكن لزر التدريب أن يبدأ training/evaluation كاملتين، مع activation وفق سياسة ترقية محددة مسبقًا أو بإجراء مستقل. سهولة البدء لا تستدعي حذف التحقق.

يحتاج التصميم المقترح إلى Admin authentication لدى Backend، وتفويض لدى الخدمة، و`job_id/status`، و idempotency مبنية على source و cutoff و recipe، وقفل للبناء المتنافس على الإصدار نفسه، و audit log، وتقدم وحالة failure، و retry آمن. تُفصل موارد التدريب عن serving، وتُكتب المخرجات في release معزولة. كل ذلك **مقترح؛ لا يوجد job runner أو Admin endpoint حاليًا**.

يرجع طلب HTTP حالة قبول مع `job_id`، ثم يعمل worker مستقل. تعرض وثائق [FastAPI Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/) حدود العمل الحسابي الثقيل داخل background tasks، وتشرح [وثائق Celery Tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html) التنفيذ والـ retries والـ idempotency. Celery مثال لخيار تشغيل، وليس شرطًا لهذا العقد.

يجب أن يثبت serving manifest إصدار Grade و Fail و category levels و GradeScale، و history cutoff/revision، و student states، و catalog والسياسات وإصدار الكود. بعد نجاح التحقق تُفعّل release ذريًا عبر pointer واحد، وتُحمّل مكوناتها معًا. rollback يعيد هذا pointer إلى release كاملة محفوظة؛ لا يخلط ملفات من إصدارات مختلفة. registry و atomic promotion والـ rollback التشغيلي غير منفذة حاليًا.

### الحد الأدنى للمرشحين

مصدر `V_CRG_STD_COR_TEMP_REQUEST` ليس catalog ثابتًا. عدد كبير من صفوفه لا يحمل `part_id`، ولا يحتوي الملف على `degree_id`. الكود الحالي يقرأ JSON أو Parquet؛ لا يشغّل إجراء قاعدة البيانات، ولا يتحقق من عزل نتائجه بين الطلبات. لا يوجد تعريف SQL محلي للإجراء يثبت السياسات التي يطبقها.

العقد المنطقي المقترح يضع السياق المشترك مرة واحدة: `student_id`, `degree_id`, `target_part`, `catalog_version`, `source_revision`, `captured_at`, ومعرّف أو hash للـ candidate snapshot، وتصريح واضح بأن القائمة تخص هذا الطالب والبرنامج والفصل وأن أهلية عناصرها قد فُحصت. يكفي `course_id` داخل كل candidate إذا كان catalog المحلي مطابقًا للإصدار الجامعي. تؤخذ ساعات المادة ونوعها ومجموعة متطلبها وترتيب السنة والفصل وحصة المجموعة من catalog، ولا تُكرر مع كل مرشح.

إذا كان Backend يرسل قائمة مختلطة من مواد مسموحة وغير مسموحة، يلزم علم أهلية موثق مثل `is_requestable` ويُختار منه `Y`. البديل الأقل تكرارًا هو إرسال قائمة المواد المسموحة فقط، مع تعريف موثق للأهلية على مستوى الطلب. يمكن إرسال `course_credits` اختياريًا للتحقق من توافق catalog؛ إذا ظهر اختلاف فلا يُستخدم كبديل صامت عن catalog، بل يُعالج اختلاف الإصدار أولًا.

هذا **عقد مقترح، وليس وصفًا لما يقبله adapter الحالي**. الدالة [normalize_candidates()](<D:/AI/Real projects/Academic_Advisor_Simple/src/recommendation/inputs.py:48>) تشترط حاليًا `course_id` و`course_credits`، وتتحقق من مطابقة الساعات مع catalog. ثم تبني الأعمدة الثمانية في `CANDIDATE_COURSE_COLUMNS`: معرف المادة، ساعاتها، `attempt_number`، وخمسة حقول catalog. قبول قائمة معرفات فقط يتطلب تعديلًا لاحقًا للـ adapter. لا توجد ضرورة معمارية لإرسال هذه الأعمدة الداخلية الثمانية كلها من PHP.

الـ adapter يفلتر `is_requestable=Y` إذا وجد العمود، ويسمح بغيابه في المدخل المحلي. لا يستخدم `allow_register`. في البيانات الفعلية يوجد 16 صفًا يحمل `is_requestable=Y` مع `allow_register=N`، و 375,518 صفًا يحمل `allow_register=Y` مع `is_requestable=N`. لذلك لا يُعامل العلمان كمرادفين. كذلك يعيد المحرك إنتاج إحصاءات التاريخ، ولا يسمح لحقول outcomes أو history المرسلة مع المرشح بتجاوزها.

لأن المصدر مؤقت ومتغير، يُفضّل أن ينفّذ Backend الإجراء، ثم يلتقط نتيجته للطالب والبرنامج والفصل داخل نطاق عزل موثوق، ثم يرسل snapshot متسقًا إلى Python. إذا كان view مشتركًا ويتغير مع كل استدعاء، ففلتر الطالب وحده لا يثبت الأمان بين طلبين لنفس الطالب لفصلين مختلفين. هل النتائج خاصة بالجلسة أو بالـ job، أم تحتاج transaction أو lock، سؤال لفريق Backend بناءً على تعريف الإجراء؛ لا يمكن إثباته من export المحلي.

### الخطة الكاملة والمواد المسجلة مسبقًا

الـ 14 feature الخاصة بالخطة والـ peers تُحسب أثناء التدريب من حمل الفصل الكامل، باستخدام roster التسجيلات `R/E`، وليس من قائمة المواد الجديدة التي يبحث الطالب عن إضافتها فقط. المصدر هو [build_registration_roster()](<D:/AI/Real projects/Academic_Advisor_Simple/src/data/build_registration_roster.py:35>) ثم [attach_plan_context()](<D:/AI/Real projects/Academic_Advisor_Simple/src/features/build_temporal_features.py:24>). أثناء serving يستخدم المحرك المواد الموجودة داخل كل خطة مولدة، عبر [score_rows()](<D:/AI/Real projects/Academic_Advisor_Simple/src/recommendation/engine.py:85>).

إذا كان الطالب مسجلًا مسبقًا في مواد **الفصل المستهدف نفسه**، أو توجد مواد إلزامية يجب أن تبقى في الخطة، فلا تكفي قائمة candidates القابلة للاختيار. يجب توفير `fixed_courses` أو مرجع موثوق لقائمة التزامات الفصل المستهدف، وإضافة هذه المواد إلى كل خطة مرة واحدة قبل حساب عدد المواد والساعات والصعوبة والـ peers. وإلا ستُحسب features على جزء من حمل الفصل ويحصل `TRAIN/SERVE SKEW`. الحقول الخام `student_id`, `course_id`, `part_id`, `register_status` موجودة في سجل المواد؛ وجود تسجيلات مستقبلية جاهزة للهدف وتوقيت إتاحتها يحتاجان تأكيد Backend.

يجب أيضًا تثبيت معنى requested credits: هل العدد هو **إجمالي حمل الفصل المستهدف** أم ساعات إضافية فوق تسجيل قائم؟ المحرك الحالي يتعامل معه كإجمالي ساعات الخطة التي يولدها. دعم ساعات إضافية يحتاج احتساب ساعات المواد الثابتة في القيد، ثم حساب الـ 14 feature على المواد الثابتة والجديدة معًا. هذا gap في العقد الحالي، وليس سلوكًا مطبقًا.

أما مواد الفصل الجاري `20261` عند التوصية لـ`20262`، فلا تُضاف تلقائيًا إلى سياق حمل `20262`. قد تؤثر على أهلية المتطلبات السابقة أو الأرصدة المحجوزة أو سياسة التسجيل للفصل القادم، حسب الجامعة. يُرسل سياقها لهذه السياسات عند الحاجة، مع فصل النتائج النهائية عن المواد التي ما زالت قيد الدراسة.

### المتطلبات والساعات الاختيارية

`requirement_type_id` موجود في catalog وفي مصدر الطلب. `credits_count` ثابت داخل كل مجموعة `(degree_id, requirement_type_id)` في البيانات المفحوصة؛ توجد 295 مجموعة، ومجموع ساعات جميع مواد catalog يتجاوز هذا الرصيد في 139 مجموعة. هذا يثبت أن جميع البدائل المدرجة ضمن المجموعة ليست بالضرورة ساعات مطلوبة كلها من الطالب. لكن البيانات وحدها لا تثبت أن هذا الرصيد يمثل سقف تسجيل صارمًا؛ يلزم التفريق بين required credits و maximum credits.

مثال البرنامج `42.111`: حصة المتطلب 1 هي 11 ساعة، والمتطلب 2 هي 4، والمتطلب 3 هي 170؛ المجموع 185. للمتطلب 2 توجد 13 مادة مجموع ساعاتها 26، رغم أن `credits_count=4`. وفي الدرجات الخمسين الموجودة في `student_status_v2`، يساوي `degree_credits_count` مجموع `credits_count` مرة واحدة لكل مجموعة، دون اختلاف في اللقطة الحالية. لا يجوز جمع `credits_count` عبر جميع صفوف المواد، لأن حصة المجموعة تتكرر في كل صف.

`requirement_passed_credits` موجود في مصدر الطلب، لكنه مفقود في 88,459 صفًا. لا يوجد دليل أنه academic audit رسمي يعالج retakes و transfers و waivers وفق جميع السياسات المطلوبة. كذلك يلزم إثبات زمن snapshot قبل استعماله كرصيد حالي.

في العينة `student_id=29485.111` و`degree_id=42.111`، يعرض مصدر الطلب 71 ساعة مجتازة للمتطلب 3، بينما التاريخ قبل `20251` يعطي 53؛ نتائج `20251` أضافت 18 ساعة. و`credits_till_grad=99` يساوي `185−86` باستخدام ساعات نهاية الفصل، بينما المتبقي عند البداية هو `185−68=117`. القيمتان تتضمنان نتائج الهدف عند replay `20251`. يمكن أن تصبحا معلومات سابقة لهدف لاحق بعد تثبيت النتائج، إذا كان توقيت snapshot واضحًا؛ لا تُعاد تسميتهما current state دون `as_of`.

العقد المقترح يرسل رصيد كل requirement مرة واحدة: `requirement_type_id`, `required_credits`, `effective_max_credits`, `completed_counted_credits`، و`reserved/in_progress_counted_credits` إذا كانت الجامعة تعتمدها، مع إصدار academic audit ومراجع تعديل الرصيد و`data_as_of`. تُرسل صلاحية تجاوز الحد ونطاق الاستثناء عند وجودهما. إذا أمكن حساب remaining بدقة من `max−completed−reserved` فلا يُطلب حقل remaining إضافي. أما إذا كان academic audit يعطي رصيدًا وفق قواعد أخرى، فيُستخدم تعريفه الرسمي بدل استبداله بصيغة مبسطة.

بعد تثبيت تعريف الجامعة، يمكن أن يكون قيد الخطة:

`completed + reserved + Σ(incremental counted credits of selected courses) <= effective maximum`.

القيمة التي تُستهلك من الرصيد ليست دائمًا `course_credits`: إعادة مادة مجتازة، أو مادة معفاة، أو مادة تُحسب بدل مادة أخرى، قد لا تزيد الساعات المحتسبة للفئة بنفس المقدار. في مثال سقف 130 وساعات مجتازة 125، دون حجز أو استثناء، يبقى 5؛ مجموع مادتين من 3 ساعات يتجاوز الرصيد. لكن `required_credits=130` وحده لا يثبت وجود hard cap يساوي 130.

السماح بكل مادة منفردة لا يضمن السماح بمجموعها. حتى لو كان الإجراء يؤكد individual eligibility، يلزم فحص رصيد المجموعة على مستوى combination، ما لم توجد آلية Backend موثقة تفحص الخطة نفسها.

لا يمكن تصنيف repeat أو prerequisites أو overflow بأنها `Already enforced by candidate procedure` اعتمادًا على القائمة وحدها. يلزم تعريف موثق للقواعد وضمان أن نتيجة الإجراء تخص snapshot المطلوب.

### Requested credit hours والمواد ذات الساعات الصفرية

الدالة [enumerate_plan_indices()](<D:/AI/Real projects/Academic_Advisor_Simple/src/recommendation/plan_generation.py:22>) تستخدم `Decimal`: `credits=18` يعني 18 بالضبط، و`min_credits=12/max_credits=18` يعني 18 بالضبط أيضًا. يُحفظ الحد الأدنى للتوثيق، لكنه لا يسمح بخطط 12 إلى 17. عند غياب combination مطابق تمامًا تكون النتيجة فارغة، دون fallback لساعات أقل. دعم جميع المجموعات ضمن 12 إلى 18 شاملًا سيكون تغييرًا لسلوك المنتج والمحرك، وليس مجرد ربط API.

قرار الـ mode والمعنى التجاري للساعات يُثبت مع المنتج و Backend. المحرك ينفذ القيد، و FastAPI لاحقًا يتحقق من العقد ولا يختار target تلقائيًا. يمكن تمثيل السلوك الحالي بـ`exact` أو `upper_bound_exact`. لا يُعرض `inclusive_range` كخيار مدعوم حتى تنفيذه واعتماده.

Catalog الحالي يحتوي مواد بساعات صفرية. المحرك يسمح باختيارها حتى بعد بلوغ target hours؛ لا ترفع مجموع الساعات أو quality points، لكنها ترفع عدد مواد الخطة والـ peers، وقد تغير `peer_max_fail_rate` لأنه غير موزون بالساعات. لذلك يمكن أن تغير توقعات المواد الأخرى، وتزيد عدد combinations؛ حذفها بحجة أنها لا تضيف ساعات يغير semantics الحالية. يجب أن يحدد max course count هل يشملها، وكذلك السياسة الأكاديمية لإعادتها. تحذير repeat الحالي قد يظهر لها عند `attempt_number>1` رغم أن مساهمتها المباشرة في additive GPA صفر.

### Current / Projected GPA

تستخدم [summarize_scored_plans()](<D:/AI/Real projects/Academic_Advisor_Simple/src/recommendation/plan_scoring.py:43>) الصيغتين:

`expected_plan_gpa = Σ(course_credits * expected_points) / Σ(course_credits)`.

`projected_cumulative_gpa = (current_gpa * current_gpa_credits + plan_quality_points) / (current_gpa_credits + plan_credits)`.

تأتي points من تحويل predicted mark، بعد قصه إلى `[0,100]`، عبر GradeScale و`grade_version_id`. لا تُحسب بقسمة متوسط العلامة على 25. الـ projection الحالي additive: لا يطرح quality points أو credits لأي محاولة سابقة. العلم `projected_gpa_requires_repeat_policy` تحذير فقط؛ لا يعدل projection أو ترتيب الخطط.

Current GPA في Local CLI يأتي افتراضيًا من `snapshot.start_agpa_points`. وترتيب اختيار المقام في [resolve_current_gpa_credits()](<D:/AI/Real projects/Academic_Advisor_Simple/src/recommendation/engine.py:21>) هو override صريح، ثم `snapshot.current_gpa_credits`، ثم `prior_total_reg_credits`. هذا اختيار في الكود، **وليس دليلًا أن `total_reg_credits` يساوي مقام GPA الرسمي**. سجل المواد الخام يحتوي `in_gpa/in_agpa/in_credits` و points، لكن قواعد استبدال الدرجات والإعادات والتحويلات ليست مثبتة. الحكم قبل وصف النتيجة بأنها projected GPA رسمي هو: **NEEDS BACKEND / UNIVERSITY CONFIRMATION**.

للحساب additive نحتاج GPA ومقامه الرسمي من snapshot واحد. وإذا كانت قيمة GPA المعروضة مدوّرة، فإن `GPA * credits` يعيد بناء quality points بصورة تقريبية. إن توفر total quality points الرسمي بدقة، يمكن اعتماد `current_quality_points + current_gpa_credits` كأساس أدق، واشتقاق GPA منه بدل طلب قيم متكررة بلا حاجة. لا يقبل المحرك الحالي هذا البديل مباشرة؛ هذه توصية للعقد اللاحق، لا وصف لتعديل منفذ.

إذا كانت الجامعة تطبق replacement عند إعادة مادة، يلزم GPA audit يحدد مساهمة المحاولة المحتسبة التي ستُزال، في quality points والـ credits، وقاعدة اختيار المحاولة: الأخيرة أو الأفضل أو غيرها. old mark بمفرده لا يكفي. إضافة هذه السياسة قد تغير projection وترتيب الخطط، وتحتاج تحققًا واعتمادًا مستقلين. كذلك لا يجوز إدخال نتائج متوقعة لمواد الفصل الجاري في current GPA الرسمي؛ إذا احتاج المنتج مثل هذا السيناريو فيُعرَّف بصورة مستقلة عن snapshot النتائج النهائية.

### Catalog ownership

Python يحتفظ بـ catalog محلي ذي إصدار معلوم، يشمل ساعات المادة ونوعها ومجموعة متطلبها وترتيبها وحصة المجموعة، و degree metadata اللازمة. GradeScale أيضًا artifact معلوم الإصدار، والمصدر الجامعي هو المرجع لتحديثهما. المرشحون الحاليون وحقائق الطالب ومقام GPA وأرصدة المتطلبات والاستثناءات تأتي من Backend أو من serving state محدث ومتوافق زمنيًا.

معرفات المواد تكفي للـ candidate lookup عندما يتطابق curriculum/catalog version بالضبط. إذا كانت المادة مجهولة أو تعارضت الساعات، فالـ adapter الحالي يفشل؛ لا يوجد silent fallback. مفتاح catalog الحالي هو `(degree_id, course_id)` ولا يوجد curriculum version داخل المصدر المحلي. إذا كان البرنامج يملك عدة خطط لطلاب مختلفين، يلزم plan/curriculum version أو سياق خطة الطالب. الربط العالمي على `course_id` وحده لا يحافظ على semantics خصائص المادة ضمن البرنامج.

يمكن أن يبقى Body الخارجي من المنتج إلى Backend/gateway صغيرًا:

هذا **لا يكفي وحده لحساب Recommendation دون Context provider**. يلتقط PHP الحقائق الحية وال Candidates مرة واحدة، ويضيف Resolved context، أو Reference إلى Snapshot مخزنة يمكن للخدمتين قراءتها. لا يرسل 47 Features ولا يعيد جلب Transcript عند كلطلب.

المثال التالي Conceptual فقط؛المعرّفات وال Revisions عناصر توضيحية وليست Registry موجودة أو بيانات طالب حقيقي:

  "target_part": 20262,

`student_state_ref` يتطلب State تحمل الحقائق اللازمة في E: Start/current facts،GPA history،Faculty/Grade version،Diploma state،و Revisions/Cutoffs. إذا لا يوجد State/reference provider تُرسل تلك القيم **inline مرة واحدة** في Context.
