# Pilot 20251 — API credit targets and search benchmark

## نطاق التقرير وحالة الدليل

هذه تجربة حسابية محلية داخل واجهة Streamlit الموحدة. معيار الترتيب هو `expected_plan_gpa` للفصل، ثم `expected_failed_credits`، ثم أعلى احتمال رسوب، ثم ترتيب DFS الحتمي الأصلي. لا تتوفر أدلة كافية لإسقاط معدل تراكمي رسمي أو اعتماد صلاحية التسجيل. نتائج الخطط البديلة ليست نتائج أكاديمية فعلية مرصودة.

حالة التنفيذ والتحقق ضمن النطاق المحلي المحدد: **PASS**. اكتمل benchmark لخمسة طلاب، مع عشرة Oracles مكتملة و190 صف مقارنة. تعميم اختيار خوارزمية واحدة على الثلاثين: **INCONCLUSIVE**. لا يُستنتج تفوق خوارزمية من اسمها أو من اكتمال pool حجمه 2000 فقط.

## 1. حل هدف الساعات من API

المصدر الحالي هو `Courses API.data.registserRule`، وتحديدًا `LOAD_TYPE=CREDIT` و`MIN_CREDITS/MAX_CREDITS`. لا تُشتق الساعات من `MAX_NEW_COURSES`، أو إجمالي ساعات المرشحين، أو قيود مجموعات المتطلبات. عند وجود `integration_context.registration_policy` موثق المصدر والفصل، تحدد قيمة `load_profile` أي حدود إضافية تُطبّق: `MIN_STUDY_CREDITS/MAX_STUDY_CREDITS` للدراسة، أو `GRAD_MIN_LIMIT/GRAD_MAX_LOAD` للتخرج. التقاطع: أكبر حد أدنى وأصغر حد أعلى. لا يُستنتج الملف من المعدل أو المواد المتاحة.

`credit_target.py` يعيد `UNRESOLVED` مع سبب عند غياب حدود أساسية أو تعارض الحدود المعنية. الافتراضي `target_credits_source=API`، والهدف هو الحد الأعلى الفعال بالضبط. إذا لم توجد مجموعة تطابقه تبقى الحالة `NO_MATCHING_PLAN`؛ لا تُخفّض الساعات. التجربة اليدوية تحتاج تفعيلًا منفصلًا وتحمل `MANUAL_DIAGNOSTIC`، وتحترم جميع الحدود الصريحة المعروفة. عناصر الإدخال اليدوي مفصولة حسب الطالب واللقطة.

Pilot العادي والمقارنة الجماعية يحلان الهدف لكل طالب بصورة مستقلة، ويحفظان الحدود والمصدر في manifest وCSV وجداول النتائج. لم تُعدّل معادلات التنبؤ أو Production FastAPI.

## 2. فضاء البحث والاستراتيجيات

تُعاد الاستفادة من `_candidates` و`build_snapshot`؛ المرشحون هم مواد API المقبولة فقط، بترتيب `course_id` الثابت. الفضاء الحالي يطبق التفرّد والساعات الدقيقة مع أهلية المرشح التي يتحقق منها Pilot. `ExactPlanSpace` يحوّل قيم `Decimal` إلى وحدات صحيحة، ويحسب عدد الإكمالات لكل `(index, remaining_credit_units)`. لا يقرّب الساعات، ويحفظ عضوية المواد ذات صفر ساعة كما يفعل مولد DFS الأصلي. أرقام الخطط العالمية هي رتب include-first DFS نفسها، مع هوية `SHA-256` لمجموعة معرفات المواد المرتبة لتسهيل المقارنة بين الطرق.

| Strategy | الاكتشاف | استدلال مودل إضافي للتوجيه |
|---|---|---|
| `FIRST_N` | أول N رتب صالحة وفق ترتيب DFS الأصلي | 0 |
| `DIVERSE_N` | عينة رتب كاملة صالحة دون إرجاع، ببذرة ثابتة | 0 |
| `SMART_SEARCH` | best-first مع حد دقيق **للمؤشر الإرشادي فقط**؛ المؤشر مجموع متوسطات العلامات التاريخية السابقة مرجحة بالساعات | 0 |

عينة `DIVERSE_N` منتظمة على الرتب في الفضاء المعرف هنا، لأن العد يطابق القيود المنفذة فعلًا. هذا لا يضمن تباعد الخطط من حيث المواد أو انخفاض Jaccard. لا تعميم لهذا الادعاء على سياسات غير منفذة. بالنسبة إلى `SMART_SEARCH`، ترتيب المؤشر التاريخي ليس حدًا أعلى لمعدل B/C، ولا يثبت ترتيبًا أمثل لتنبؤاتهما. غياب القيمة التاريخية يعطي مؤشر توجيه صفريًا فقط؛ لا تُملأ ميزات المودل بهذه القيمة. المؤشر مشترك بين B وC، ولذلك يقيم المودلان مجموعات الخطط المختارة نفسها.

بعض سياسات مجموعات المتطلبات والإعادة و`MAX_NEW_COURSES` غير مؤكدة في Pilot الحالي. تظل هذه الحالات معلّمة صراحة، ولا نختلق caps أو نزيل قيدًا مثبتًا. إذا ظهر عقد سياسة مؤكد جديد لا يعرف هذا الفضاء تمثيله، يُحجب benchmark بدل تجاهله. لا تعتمد أي نتيجة بوصفها خطة تسجيل رسمية.

## 3. تجربة الـ2000-pool

`FIXED_POOL` يحفظ أول ما يصل إلى 2000 رتبة صالحة من DFS، هويات الخطط وبصمة المجموعة. تختار الطرق الثلاث داخل هذه المجموعة حصريًا. عند ميزانية 2000 ومع pool مكتمل من 2000 خطة، تقيّم الطرق المجموعة نفسها؛ تساوي أفضل ثلاث خطط فحص اتساق متوقع. هذا القياس لا يختبر الوصول إلى خطط خارج البادئة.

## 4. تجربة الفضاء الكامل

`FULL_SPACE` يستخدم العد والرتب على فضاء المرشحين الكامل، ولا يقرأ oracle أو نتائج pool لاكتشاف المرشحين. الميزانيات 200 و1000 و2000 تقيد عدد الخطط الكاملة الفريدة التي يتنبأ بها **كل مودل في كل تجربة**. تقييم B وC لعينة N مشتركة يعني N تقييمًا لكل منهما. كل تجربة تقيم عينتها فعلًا؛ لا تُخفى استدعاءات كاملة ضمن التحضير أو يعاد استخدام ترتيب oracle.

يُحفظ عدد حالات التحضير والاختيار، عدد الخطط المكتشفة والمقيّمة، حجم الفضاء ونسبة التغطية والقطع. تشمل الأزمنة تحضير السياق والميزات، الاختيار والمؤشر الإرشادي، استدلال المودل، الترتيب والحفظ. `standalone_runtime_seconds` يضيف التحضير المشترك بصورة محافظة إلى صف المقارنة؛ لا تجمع صفوف B/C أو الميزانيات لأن بعض التحضير والاختيار مشترك. مجموع المحاولة الفعلي موجود في manifest، مع مجموع المحاولات عند الاستئناف.

## 5. Exhaustive Oracle والحفظ

`EXHAUSTIVE` يمر على كل رتبة صالحة دون سقف 2000. يعاد بناء سياق الخطة الكاملة بـ`build_plan_rows` ويمر كل صف عبر B/C `predict_course_rows` الأصلي؛ ثم يستخدم `_attach_scores` الأصلي. لا تُخزّن تنبؤات المادة على أنها ثابتة بين الخطط.

يحتفظ SQLite بملخص صغير لكل خطة، وبالتفاصيل الموسعة لأفضل ثلاث خطط فقط. تحفظ المعاملة نفسها الدرجات، المؤشر التالي، بصمة متسلسلة، وأفضل ثلاث خطط. يتحقق الاستئناف من بصمات المدخلات والمرشحين والهدف والمودل والكود؛ تُثبّت هوية عينة البحث وترتيبها. يتحقق القارئ من بصمات الملفات، ومن اتصال رتب oracle وعدم تكرارها وتطابق Top 3 مع ترتيب سجل الدرجات كاملًا. لا تُحمّل جميع صفوف المواد والخطط الموسعة في الذاكرة.

يتطلب `EXHAUSTIVE_COMPLETE` مساواة العدد المقيّم بالعدد الكامل، ومرور فحوص التكامل. أي توقف عند حدود الوقت أو عدد الخطط أو الذاكرة أو التخزين يحفظ `EXHAUSTIVE_INCOMPLETE`، وتبقى مقارنة oracle العالمية غير متاحة. الحدود تعاونية بين الدفعات؛ قد تتجاوز آخر دفعة زمن الإيقاف بقليل. توجد حدود مستقلة لحالات العد/البحث، ودفعات بحد أقصى 512 خطة. لا يبدأ التشغيل تلقائيًا لجميع الطلاب.

## 6. المقاييس ومقارنة أفضل ثلاث خطط

`GPA Gap = oracle_best_expected_gpa - search_best_expected_gpa` ضمن المودل نفسه. يقيس exact Top-3 Recall وجود هويات oracle الثلاث بين **جميع** الخطط التي اكتشفتها الطريقة وقيمتها. يقيس score-equivalent recall مطابقة قيم GPA مع تعدد التعادلات وبسماحية `1e-10`؛ لا يغيّر قواعد ترتيب Pilot. Jaccard وعدد المواد المشتركة بين الأزواج الثلاثة تشخيص للتشابه، وليسا هدف ترتيب بديلًا.

يحفظ كل صف Top 1/2/3 بالهوية القياسية وترتيب DFS والمواد والأسماء والساعات والعلامات والنقاط واحتمال الرسوب ومعدل الخطة وساعات الرسوب المتوقعة. تُعرض التفاصيل من النتائج المحفوظة في `🔎 Search Benchmark`. لا يؤدي فتح النتائج أو تحديث واجهة Streamlit إلى تشغيل inference.

تغطي اختبارات AppTest واجهتي Production/Pilot والـSearch Benchmark ضمن التطبيق نفسه، والتشغيل الصريح، وبقاء عرض النتائج وإعادة العرض بلا inference، وعزل Before/After والهدف اليدوي لكل طالب. أثبتت اختبارات الموارد انقطاع oracle واستئنافه، والميزانيات وعدم التكرار، وتلف السجل أو Top-3، وتجاوز العد `2^63` دون تحميل الفضاء في الذاكرة. نتائج الاختبارات النهائية محفوظة في ملفات JUnit داخل مجلد audit.
