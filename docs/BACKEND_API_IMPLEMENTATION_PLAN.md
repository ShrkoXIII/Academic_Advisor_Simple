# الخطة المعتمدة لدمج Backend API

هذه نسخة تنفيذية للخطة المعدّلة التي اعتمدها المستخدم في 2026-10-10. اعتماد التنفيذ لا يثبت جاهزية المدخلات الحقيقية أو أداء الإنتاج. التقرير النهائي في [تقرير التنفيذ](../reports/backend_api_integration.md)، والعقد التفصيلي في [README](../src/api/README.md).

## النطاق والقرارات الملزمة

1. إنشاء `src/api/` فوق محرك Two-Stage الحالي، وإعادة استخدام خريطة `graphify` والكود الفعلي. الترتيب الافتراضي `pareto v1 → pareto v1` و`Top 3`، مع بوابة اعتماد manifest الأصلية.
2. تبعيات HTTP اختيارية. استيراد الحزمة لا يقرأ المودلات أو التاريخ. تحميل التبعيات مستقل أثناء `lifespan`؛ فشل إحداها لا يمنع HTTP أو واجهات التحقق.
3. لا تدريب، ولا تعديل لعقود 33/47 ميزة أو خوارزميات الترتيب أو الأصول المحمية، ولا توصيات للطالب الحقيقي، ولا Git commit.
4. لا حد ثابت من 17 مادة. `performance_test_max_candidates` إعداد صريح يُطبق في وضع اختبار الأداء فقط؛ التجاوز يرفض الطلب كاملًا دون اقتطاع. التحقق يحلل كل المواد. حدود الإنتاج `UNRESOLVED`.
5. مطلوب سياق مستقل لكل جلب في `source_contexts.student` و`source_contexts.courses`، مطابق لهوية الطلب. التحقق من هوية المحتوى يسبق التصفية. Courses بلا هوية يُوسم `php_attested`.
6. PHP مسؤول عن توثيق المستخدم وصلاحياته وجلب الردين بالسياق الصحيح. Python يوثق خدمة PHP ويثبت اتساق البيانات. مفاتيح الخدمة والإدارة منفصلة؛ الاستجابات والأخطاء لا تعيد المدخلات الخام أو البيانات الشخصية أو المسارات الخاصة.
7. `studentSummaryInfo` يُفحص قبل الحساب. الحساب الأصلي الكامل يُستخدم عند توافق schema، وحساب GPA المشترك النقي يُستخدم عند توفر أعمدته فقط. لا عدادات أو مقامات أو قيم افتراضية لتعويض النقص. الحفاظ على الفصول غير المسجلة وgaps وGPA السابق.
8. الدبلوم ومقام GPA الرسمي مطلوبان. `integration_context` يحتاج مصدرًا وcutoff قبل الهدف، ويرفض التعارض مع المصدر الأصلي المكافئ.
9. IDs سلاسل، والمحاولة الحالية `ATTEMPTS_COUNT + 1`. `plan_course_type_id` من كتالوج الاختصاص. حالة الإعادة والاستثناء تحتاجان مصدرًا مؤكدًا. سياسات المتطلبات مرتبطة بـdegree و`REQUIREMENT_ID`، مستقلة عن تصنيف المودل. `max_new_courses` اختياري.
10. تقاطع الساعات المطلوبة مع الحدود المؤكدة ثم الهدف الأعلى الدقيق، دون fallback. حفظ `allowRegisterAllOptional` دون تحويله إلى تجاوز مطلق.
11. API تمرر cutoff صريحة دائمًا. `normal` يستخدم الفصل السابق وفق `previous_academic_part()`؛ الأقدم يحتاج `backtesting` صريحًا وتفعيل الخدمة. لا هدف/مستقبل ولا تجاوز cutoff التدريب. اختيار الحزمة بالضبط، وتثبيت Snapshot طوال الطلب. استدعاءات Core القديمة تحتفظ بسلوكها.
12. Delta تحقق ومعاينة إدارية فقط. إعادة استخدام schema والمجاميع وreplay والتعارض. تثبيت الفصل منفصل عن سلامة المجاميع. لا publish/commit/activation ولا تقدير `points_sum`.

## مراحل التنفيذ والقبول

| المرحلة | الناتج | دليل القبول |
|---|---|---|
| A: تدقيق وخط أساس | قراءة المخطط والكود وschemas وحصر الأصول | سجل baseline وبصمات قبل التنفيذ |
| B: الربط المشترك | helper GPA وقيود المجموعات وcutoff اختيارية ومعاينة Delta | توافق سابق، تطابق الحساب، ثبات fingerprint القديم |
| C: Adapters | طالب ومواد وDelta مستقلون | هوية، schema، قيم ناقصة، مصادر، gaps، أرقام، تكرار، استثناءات |
| D: HTTP | الواجهات الخمس وauth وhealth مستقل | بدء HTTP دون موارد، 422/409/503، صفر inference عند الرفض، تعقيم الأخطاء |
| E: التكامل | محرك معتمد بمودلات اصطناعية | 33/47، Top 3، Pareto/Pareto، قيود دقيقة، backtesting، حد الأداء |
| F: التسليم | README وتقرير PASS/PARTIAL/BLOCKED | مركّزة ثم مرتبطة ثم كاملة، مقارنة hash، Git، تحديث graphify AST |

واجهات التنفيذ: `POST /api/v1/inputs/student/validate`، `POST /api/v1/inputs/courses/validate`، `POST /api/v1/recommendations`، `POST /api/v1/history/deltas/validate`، `GET /health`.

Fixtures من المثالين عبر allowlist وتنقيح هوية الطالب، مع مصادر اصطناعية واضحة لمسار النجاح. مقارنة baseline إلزامية؛ لا يُنسب فشل `capaciy_63` مقابل `capacity_63` إلى API.
